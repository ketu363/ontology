clicking **Save Ontology to BigQuery** currently stores only the latest **TBox ontology**—classes, attributes, relationships, and reasoning. It does not send the CSV files or ABox records.

## Complete execution flow

```text
Ontology generated by LLM
        ↓
Stored in backend memory using session_id
        ↓
User clicks “Save Ontology to BigQuery”
        ↓
Frontend sends only session_id
        ↓
Backend retrieves the current ontology
        ↓
Entities become graph_nodes rows
Relationships become graph_edges rows
        ↓
BigQuery tables and filtered views are created
        ↓
CREATE OR REPLACE PROPERTY GRAPH ontology_pg
        ↓
BigQuery Graph page displays the classes and relationships
```

## 9. Why filtered views are created

Originally, if the property graph directly used only the generic `graph_nodes` table, BigQuery saw:

```text
One node table → one graph node type
One edge table → self-loop
```

That produced the earlier incorrect-looking single-node graph.

The explanation is documented at [bigquery_service.py:380](C:/Users/niketu/Downloads/ontology-agent/backend/app/bigquery_service.py:380).

To solve this, the code creates one filtered view for every ontology class and relationship.

For a `Vehicle` class, it creates SQL conceptually like:

```sql
CREATE OR REPLACE VIEW `_ontology_pg_node_vehicle_...` AS
SELECT *
FROM `ontology_graph.graph_nodes`
WHERE graph_version_id = 'tbox_abc123'
  AND node_id = 'Vehicle';
```

This happens at [bigquery_service.py:401](C:/Users/niketu/Downloads/ontology-agent/backend/app/bigquery_service.py:401).

For a relationship:

```text
Vehicle -[ASSIGNED_TO]-> Depot
```

It creates another filtered view:

```sql
CREATE OR REPLACE VIEW `_ontology_pg_edge_vehicle_assigned_to_depot_...` AS
SELECT *
FROM `ontology_graph.graph_edges`
WHERE graph_version_id = 'tbox_abc123'
  AND source_id = 'Vehicle'
  AND relationship_type = 'ASSIGNED_TO'
  AND target_id = 'Depot';
```

This happens at [bigquery_service.py:433](C:/Users/niketu/Downloads/ontology-agent/backend/app/bigquery_service.py:433).

The hashed part of the generated view name comes from `_element_name()` at [bigquery_service.py:41](C:/Users/niketu/Downloads/ontology-agent/backend/app/bigquery_service.py:41). It makes names stable and avoids collisions.

## 10. The actual `ontology_pg` graph is created

The graph SQL is assembled at [bigquery_service.py:475](C:/Users/niketu/Downloads/ontology-agent/backend/app/bigquery_service.py:475):

```sql
CREATE OR REPLACE PROPERTY GRAPH
  `project.dataset.ontology_pg`

NODE TABLES (
    vehicle_view AS vehicle_node
      KEY (graph_version_id, node_id)
      LABEL Vehicle,

    depot_view AS depot_node
      KEY (graph_version_id, node_id)
      LABEL Depot
)

EDGE TABLES (
    assigned_to_view AS assigned_to_edge
      KEY (graph_version_id, edge_id)
      SOURCE KEY (graph_version_id, source_id)
        REFERENCES vehicle_node
      DESTINATION KEY (graph_version_id, target_id)
        REFERENCES depot_node
      LABEL ASSIGNED_TO
);
```

The complete SQL script is executed at [bigquery_service.py:357](C:/Users/niketu/Downloads/ontology-agent/backend/app/bigquery_service.py:357):

```python

This creates:

      └── ontology_pg
```

`ontology_pg` is not another data table. It is a BigQuery `PROPERTY GRAPH` definition that connects the node and relationship views.

## 11. Why BigQuery now shows multiple nodes

BigQuery’s Graph overview displays one schema element for every node-table definition.

Because the code creates separate filtered views, BigQuery can display:

```text
Vehicle ──ASSIGNED_TO──> Depot
Driver ──OPERATES──> Vehicle
Vehicle ──HAS_MAINTENANCE──> ServiceLog
```

That is why your new screenshot correctly shows 12 nodes and 13 edges instead of one node with a self-loop.

## 12. The version manifest is saved last

After tables, views and the property graph are successfully created, the code inserts a row into `graph_versions` at [bigquery_service.py:300](C:/Users/niketu/Downloads/ontology-agent/backend/app/bigquery_service.py:300).

It is intentionally saved last so that `graph_versions` only reports a version as complete after its nodes, edges and graph definition are created.

One technical detail: BigQuery operations here are not one database transaction. If graph creation fails after node rows are written, some unregistered rows can remain in the node/edge tables, but no completed entry is added to `graph_versions`.

## What happens on every Save click?

Every click does the following:

1. Gets the latest ontology from the current UI session.
2. Creates a new `tbox_<uuid>` version.
3. Appends new rows to `graph_nodes`.
4. Appends new rows to `graph_edges`.
5. Recreates the filtered views for the latest ontology.
6. Replaces `ontology_pg` with the latest TBox definition.
7. Adds the completed snapshot to `graph_versions`.

So:

- The three tables retain historical versions.
- `Graphs → ontology_pg` displays the latest saved TBox.
- It currently does not save ABox instances.
- It does not save the original CSV rows.
- Saving the same ontology twice creates two stored versions.

The BigQuery configuration is loaded from environment variables at [bigquery_service.py:69](C:/Users/niketu/Downloads/ontology-agent/backend/app/bigquery_service.py:69), and the shared `graph_store` is created at [bigquery_service.py:546](C:/Users/niketu/Downloads/ontology-agent/backend/app/bigquery_service.py:546). Because this happens when the backend starts, environment changes require a backend restart.
